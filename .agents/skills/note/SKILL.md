# Note — 知识点与问题归档记录

将对话中讲解的技术知识点或开发中遇到的 bug 保存到项目根目录的 [`知识/`](../../../personal_docs/项目开发/开发日志/知识/) 或 [`问题归档/`](../../../personal_docs/项目开发/开发日志/问题归档/) 目录中。

## 触发方式

用户在对话中说以下关键词时触发：

- 「记下来」「保存这个知识点」「记录一下」「这个知识点记一下」「存一下」
- 「归档这个 bug」「记一下这个 bug」
- 或其他明确表示想保存当前讲解内容或问题的意图

## 工作流

### 1. 询问记录类型

用户触发后，先询问要记录的是**知识**还是**问题归档**：

> 要记录哪种类型？
> 
> 1. **知识** — 学到的技术知识点
> 2. **问题归档** — 开发中遇到的 bug 及解决方案

根据用户选择进入对应分支。如果上下文已明显表明是哪种类型，可以直接确认而非询问。

### 2. 知识记录分支

询问用户想要记录哪个知识点，根据上下文总结后写入。

#### 路径规则

```
personal_docs/项目开发/开发日志/知识/年-月-日/时-分-{文档名称}.md
```

- `年-月-日` — 以对话当天的日期为文件夹名
- `时-分` — 文件以时间开头保证排序，如 `22-11`
- `文档名称` — 简短的文档名，如 `Win32-架构命名辨析`

示例：[`知识/2026-05-26/22-11-Win32-架构命名辨析.md`](../../../personal_docs/项目开发/开发日志/知识/2026-05-26/22-11-Win32-架构命名辨析.md)

#### 文件内容结构

**YAML frontmatter**：

```yaml
---
time: 2026-05-26 22:11
name: 文档名称（简短概括，中文）
description: 文档内容的简要描述（一句话）
problem-from: 用户当时正在解决什么问题，解决这个问题中遇到了哪个不懂的知识点
---
```

字段说明：

| 字段 | 说明 |
|------|------|
| `time` | 文档生成时间，格式 `YYYY-MM-DD HH:mm`（24小时制，精确到分钟） |
| `name` | 简短的中文名称，概括知识点 |
| `description` | 一句话描述文档内容 |
| `problem-from` | 问题回溯。记录用户当时正在解决什么问题、遇到了哪个不懂的知识点 |

**正文末尾**附加 `## 回溯上下文` 章节（同原有格式），包含：

- **问题来源** — 详细描述用户当时的使用场景和困惑
- **涉及文件** — 按问题排查路径顺序列出

正文用 Markdown 格式，完整记录知识点内容。尽量结构清晰（标题层级、表格、代码块等），方便日后阅读。

### 3. 问题归档分支

询问用户要归档哪个 bug，根据上下文总结后写入。

#### 路径规则

```
personal_docs/项目开发/开发日志/问题归档/年/月-日-{!是否可复用}-{文档名称}.md
```

- `年` — 以年份为文件夹名，如 `2026`
- `月-日` — 文件以月-日开头保证排序，如 `05-29`
- `是否可复用` — 如果该解决方案可复用，在月-日后加 `!`，如 `05-29-!-NSIS-CRC完整性校验失败.md`；不可复用则不写
- `文档名称` — 简短的文档名，如 `NSIS-CRC完整性校验失败`

示例：[`问题归档/2026/05-29-NSIS-CRC完整性校验失败.md`](../../../personal_docs/项目开发/开发日志/问题归档/2026/05-29-NSIS-CRC完整性校验失败.md)

#### 文件内容结构

**YAML frontmatter**：

```yaml
---
time: 2026-05-29 22:00
commit: a1b2c3d
name: 问题名称（简短概括，中文）
reusable: true
description: 什么情况下遇到什么问题
---
```

字段说明：

| 字段 | 说明 |
|------|------|
| `time` | 文档创建时间，格式 `YYYY-MM-DD HH:mm` |
| `commit` | 对应修复该问题的 commit hash（省略前缀，完整长度） |
| `name` | 简短的中文名称，概括问题 |
| `reusable` | `true` / `false`，该解决方案是否可复用 |
| `description` | 问题描述：什么情况下遇到什么问题 |

**正文**部分记录问题的**解决办法**，需要具体细致，逻辑链清晰。包含：

- **问题根因** — 导致 bug 的根本原因是什么
- **排查过程** — 如何一步步定位到问题
- **解决方案** — 具体的修复方式（代码/配置变更等）
- **关键文件** — 涉及的代码文件及对应改动

正文用 Markdown 格式，完整记录问题解决过程，方便日后回溯。

### 4. 关联截图（可选）

文档写入后，询问用户是否有相关的截图/图片要一起归档：

> 是否有相关的截图需要一起保存？如有，请提供图片路径。

如果用户提供了图片：

1. 将图片复制到 [`问题归档/年/images/`](../../../personal_docs/项目开发/开发日志/问题归档/)`月-日-{!是否可复用}-{文档名称}/` 目录下
2. 按顺序命名为 `01-描述.png`、`02-描述.png` 等（描述为该图内容的简短概括）
3. 在文档开头（frontmatter 之后）插入图片引用：

   ```markdown
   ![描述](images/月-日-{!是否可复用}-{文档名称}/01-描述.png)
   ```

### 5. 验证

确认文件已成功写入对应目录下，告知用户文件路径。

## 注意事项

- [`知识/`](../../../personal_docs/项目开发/开发日志/知识/) 和 [`问题归档/`](../../../personal_docs/项目开发/开发日志/问题归档/) 目录已在 `.gitignore` 中，不会被提交到 Git 仓库，仅供本地查阅
- 同一天有多个记录，分别存为不同文件
- `problem-from` 和涉及文件是回溯的关键，务必写具体，不要笼统
- 问题归档的 `description` 要能清晰描述什么场景下触发了什么异常
- 可复用的问题归档在文件名加 `!`（如 `05-29-!-NSIS-CRC完整性校验失败.md`），不可复用或一次性问题不加
- 问题归档的图片统一存放在 [`问题归档/年/images/`](../../../personal_docs/项目开发/开发日志/问题归档/)`月-日-{文档名称}/` 目录下，每个归档问题各自对应一个图片子文件夹
